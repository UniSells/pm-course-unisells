# Класифікація та аналіз оточення проєкту UniSells

## 5.1. Класифікація проєкту

| Ознака класифікації | Обрана категорія | Обґрунтування |
| :--- | :--- | :--- |
| **Розмір проєкту** | середній | Проєкт виконується командою з 4 осіб у межах студентського курсу з обмеженими термінами здачі. Обсяг функціональності орієнтований на розробку робочого MVP. |
| **Тип продукту** | веб-застосунок | Продукт створюється як Responsive Web Application з підтримкою кросбраузерності та коректного відображення на мобільних і десктопних пристроях. |
| **Галузь застосування** | e-commerce | Проєкт функціонує як двосторонній IT-маркетплейс послуг, де об'єктом купівлі-продажу виступає виконання технічних завдань. |
| **Рівень невизначеності вимог** | високий (вимоги змінюватимуться) | Продукт містить експериментальні механіки: нелінійну систему грейдування, алгоритми оцінки завдань ботом та динамічну формулу MMR. Такі параметри неможливо зафіксувати остаточно без тривалого тестування на користувачах. |
| **Модель співпраці** | стартап | Платформа розробляється за P2P / C2C моделлю для перевірки бізнес-гіпотези щодо зменшення конкуренції для новачків. Проєкт не має зовнішнього комерційного замовника. |
| **Тип життєвого циклу** | гнучкий (Agile) | Високий рівень невизначеності вимог та експериментальні формули нарахування рейтингу вимагають коротких ітерацій і швидкого внесення змін за результатами зворотного зв'язку. |

## 5.2. Аналіз внутрішнього оточення

* **Склад і компетенції команди:** Команда включає ролі PM, PO, Developer та Designer. Оскільки розробкою займається один програміст, архітектурні завдання бекенду та фронтенду зосереджені на одному виконавцеві.
* **Наявні технічні ресурси (Backend):** Використовується .NET 8 (ASP.NET Core Web API) за принципами Clean Architecture, Entity Framework Core та PostgreSQL.
* **Наявні технічні ресурси (Frontend):** Клієнт розробляється на React (TypeScript) зі збирачем Vite, інтерфейс створюється за допомогою Bootstrap 5, стан регулюється Zustand і React Query.
* **Наявні технічні ресурси (Storage & Real-Time):** Застосовується PostgreSQL для реляційних даних, Redis для кешування та In-Memory операцій, а SignalR забезпечує чат і сповіщення.
* **Часовий бюджет команди:** Кожен учасник команди виділяє орієнтовно 3–4 години на день (20–28 годин на тиждень), поєднуючи проєкт із навчальним процесом.
* **Організаційне середовище:** Проєкт реалізується в академічному середовищі університету з фіксованими проміжними контрольними точками та дедлайнами здачі етапів.

## 5.3. Аналіз зовнішнього оточення

* **Цільова аудиторія та її потреби:** Junior-фахівці, яким необхідні перші комерційні кейси без надлишкової конкуренції з досвідченими виконавцями, а також замовники, зацікавлені у гарантованій кваліфікації виконавців.
* **Наявні аналоги і конкуренти:**
  * *Upwork* — глобальний сервіс із високим рівнем конкуренції та відсутністю автоматичного відсікання виконавців за перевіреними рангами.
  * *Freelancehunt* — регіональна біржа, де сортування замовлень переважно ручне, що ускладнює пошук відповідних завдань.
* **Технологічні тренди:** Впровадження Real-Time рішень (SignalR) для швидкої комунікації, а також використання автоматизованого аналізу ТЗ для визначення складності завдань.
* **Регуляторні та безпекові чинники:** Необхідність захисту конфіденційності користувачів, верифікації даних та надійного контролю доступу через JWT і Policy-Based Authorization.
* **Партнерські системи та зовнішні API:** У перспективі потрібна інтеграція платіжних систем для холдування коштів та зовнішніх репозиторіїв (GitHub API) для аналізу коду розробників.

## 5.4. Обмеження та припущення проєкту

### Обмеження
| № | Обмеження | Категорія |
| :--- | :--- | :--- |
| 1 | Часовий бюджет команди суворо лімітований: 3–4 години на день на кожного учасника. | час |
| 2 | Реалізацію всього програмного коду (API, клієнт, БД) виконує лише один розробник. | ресурси |
| 3 | Система рангів жорстко зафіксована структурою: 5 основних рівнів по 3 підранги (зірки) кожен. | технології |
| 4 | Обмеження доступу до подачі заявок налаштовується на рівні бекенду (Custom Authorization Policy з поверненням 403 Forbidden). | технології |

### Припущення
| № | Припущення | Обґрунтування |
| :--- | :--- | :--- |
| 1 | Виділеного часу в 3–4 години на день вистачить для своєчасного створення MVP до завершення семестру. | Робота ведеться щоденно та фокусується виключно на критичній функціональності. |
| 2 | Математична формула MMR буде змінюватися в процесі тестування. | Вплив штрафів, оцінок замовника та коефіцієнтів бота вимагатиме калібрування балансу. |
| 3 | In-Memory база Redis ефективно знизить навантаження на PostgreSQL при роботі чату та перегляді замовлень. | Кешування гарячих даних прискорить відгук застосунку за умов обмежених серверних потужностей. |
| 4 | Алгоритм визначення складності завдань (від 1.10 до 1.20) адекватно оцінюватиме тексти ТЗ. | Припускається, що аналіз тексту дозволить виставити об'єктивний базовий коефіцієнт для задачі. |

## 5.5. Висновки

Класифікація продукту як e-commerce маркетплейсу з високим рівнем невизначеності вимог робить застосування Agile-підходу безальтернативним. Постійне коригування алгоритмів підрахунку MMR, системи Skill-Gating та поведінки користувачів неможливо вкласти у жорсткий план, тому розробка має вестися короткими ітераціями.

Головним критичним чинником внутрішнього середовища є високе навантаження на єдиного розробника. Навіть за умов наявності 3–4 робочих годин на день, одночасне налаштування складного бекенду (.NET 8, Clean Architecture, SignalR, Redis) та фронтенду (React, TypeScript) створює високий ризик затримок у реалізації окремих модулів.

Основні ризики на поточному етапі — це можливий дисбаланс у розрахунку рейтингу через похибки бота при оцінці складності завдань, а також імовірність перевантаження бази даних при зростанні кількості паралельних SignalR-з'єднань у чаті.

З урахуванням цього аналізу першочерговими кроками команди визначено: чітке розбиття задач на дрібні таски, першочергову реалізацію ядра авторизації та фільтрації Smart Feed на рівні SQL/EF Core, а також створення прототипу калькулятора MMR для раннього тестування формули.
